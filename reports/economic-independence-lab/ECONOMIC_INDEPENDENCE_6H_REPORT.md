## 0. 装置与机制 Bug（§68：发现即停止相关结论、修复、重跑、公开）

这一节是本轮**最需要先读**的部分。两个 Bug 都会直接污染上一轮的数字。

### Bug ①（上一轮正式机制）：`emergencyRescue.extraDays` 的语义被实现反了

- **现象**：配置注释、UI 文案、Bot 判据、规则页四处都写的是「求援**换回** N 天」，
  但引擎 `EMERGENCY_RESCUE` 分支里调用的是 `addDays(s, cfg.extraDays)`，
  而 `addDays()` 推进的是**已用天数**——于是「买回 5 天」被实际执行成「**倒扣 5 天**」。
- **后果**：求援成了一个会加速 TIMEOUT 的东西。上一轮 Phase C 里 H1（rescue400）把
  Completion 从基线 80.00% 拉到 71.56%，EH1 大样本 69.98% ——
  **这 10pp 的"下降"不是机制在救人，而是机制在害人**。
  这与本轮 §23「不得靠提高死亡概率来压指标」属于同一类问题。
- **连带后果**：上一轮报告的「首要失败原因 INSUFFICIENT_TIME 55.9%」也是这个 Bug 造出来的
  （修正后时间类失败几乎归零，剩下的 97.65% 全是耐力）。
- **修复**：`s.maxDays += cfg.extraDays`（延长**期限**，与文案一致）。
- **重跑**：修正后重新标定 —— 完成率 82.63%（BASE）/ 87.4%（OutcomeMasterBot）/ **77.27%（完全关闭求援）**。
  已新增回归测试 `tests/economy.settlement.test.ts`：「求援后 maxDays 增加 extraDays，daysUsed 不受影响」。

### Bug ②（实验装置，影响此前**全部**实验）：FairView 泄漏隐藏矿价

- **现象**：规则页 §十一 明确写着「游戏全程**不显示**矿区精确单价，成功返城后进行最终鉴定」，
  但 `buildFairMap()` 把**所有矿区**（包括从未去过的那座）的 `gemPrice` 与 `detail.jitter`
  原封不动放进了玩家视角 FairView。
- **后果**：此前所有 Bot 都在「全知价格」下做决策 —— H10（无隐藏价格泄漏）事实上从未通过。
  对**本轮尤其致命**：延期求援的核心决策就是「我这批货值不值这笔债」，
  Bot 若能精确知道货值，这个决策就恒等于一个确定性查表，机制结论完全失真。
- **修复**：`FairMap.mines` 只保留 `{tileId, slot, difficultyScore}`；`FairTile.minePrice` 置空；
  新增 `rules.marketReferencePrice`（城里打听得到的行情参考价 = 公开价格区间中点 **230 元/kg**），
  **刻意保留 ±40% 的不确定性**——正因为估不准，「赌一把叫了救援，结果鉴定价很低」才会真实发生。
- **重跑**：修正了把泄漏当成预期行为的 `tests/simulation.test.ts` 断言；全量回归重跑。

### 装置缺陷 ③：Bot 的采矿安全余量是写死的，经济机制无法影响它

- **现象**：`miningMarginal()` 用固定 `buffer = 5` 决定"再挖一天还安不安全"。
  于是任何**只改结算数字**的机制都无法改变行为 ——
  实测 `B1-P80`（每天 80 元运营费）的 Δdecision = **0%**，会被判成「统一税」。
- **后果**：不修这个，本轮**根本没有能力区分"真机制"和"统一税"**（§16）。
- **修复**：新增 `economicBuffer()` —— 风险偏好改为**经济内生**：
  按当前货值估算的预期利润越低，玩家越愿意压缩安全余量多挖一天。
  修复后同一候选 Δdecision 从 0% → **59.9%**（Phase A2 复测）。
  机制全关时预期利润本来就高，因此 buffer 不会下调，**不污染基线**。

### ★ 三个决定性发现（都是**可推导**的，不是"试了不行"）

**发现 ④：A 族（延期求援）单独使用会「提高」盈利率，而不是降低。**

| 候选 | Completion | Profitability | 求援使用率 |
|---|---:|---:|---:|
| BASE | 82.7% | 82.7% | 23.4% |
| A1-D800（债务 800） | 87.8% | **87.8%** | 39.9% |
| A1-D1600 | 87.1% | 86.6% | 25.1% |
| A1-D2400 | 81.0% | 80.7% | 8.7% |

推导：不求援 = 必亏（宝石归零）；求援 = 收入 − 债务。
理性代理只在「收入 > 债务」时叫救援 ⇒ **被救回来的局几乎必然仍然盈利**。
所以延期求援**在结构上无法单独把盈利率拉下来** —— 它提高完成率，也提高盈利率。
（这也是 §8 那条路线的真实极限，不是参数没搜够。）

**发现 ⑤：完成率 ≈80% 时，三个目标在数学上不可能同时成立。**
目标「失败 30% + 成功亏损 25% + 成功盈利 45%」之和 = 100%，**隐含完成率必须 = 70%**。
在完成率 80.75% 下，要么 `盈利 45% / 亏损 35.8%`，要么 `盈利 55.7% / 亏损 25%`。
⇒ 必须先把完成率标定回 70%，否则 G2 与 G4 二选一。

**发现 ⑥：失败原因 95~100% 集中在 `STAMINA_EXHAUSTED`。**
修正 Bug ① 后 TIMEOUT 几乎消失，耐力成了唯一死因。这是既有结构问题（BASE 也是 99.3%），
不是本轮机制造成，但确实触发 §24 拒绝线，见 §6.2。
